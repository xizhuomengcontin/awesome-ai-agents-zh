# 中文实操：把需求缩成一个可验证的 Agent 小实验

目标：用你自己准备的三份公开产品说明，生成一张包含产品名、适用场景、来源段落的比较表。不要从“搭一个全能多 agent 系统”开始。

## 1. 先选工作方式

| 你的任务 | 先看哪类工具 | 本轮先不做什么 |
| --- | --- | --- |
| 在现有仓库修一个 Bug | AI 编程助手，如 Aider、Continue | 不引入业务工作流框架 |
| Python 程序需要结构化输出 | [Pydantic AI 官方文档](https://pydantic.dev/docs/ai/) | 不让类型校验代替事实核查 |
| Python/.NET 系统需要多步编排 | [Microsoft Agent Framework](https://github.com/microsoft/agent-framework) | 不先开多个拥有写权限的 agent |
| 排查 MCP 连接 | 协议文档与受信任的诊断工具 | 不随意启动网上复制的 server 命令 |

这张表是选型起点，不是性能排行榜。本页没有替你运行任何收费模型。

## 2. 准备最小输入与验收标准

建立独立 Git 分支。只放三份公开说明，不放客户文件、密钥或完整浏览器数据。记录工具版本、模型名称和日期。

可复制的任务说明：

```text
只读取 inputs/ 中我提供的三份产品说明，生成 outputs/comparison.md。
每行包括：产品名、适用场景、原文段落编号、缺失信息。
不得联网补全，不运行安装命令，不修改 inputs/。
无法从输入证明的内容标记为“未提供”，不要猜测。
完成后列出修改文件，并说明哪些检查通过、哪些没有执行。
```

开始前固定四个验收点：恰好三行产品；每行有可定位的来源；缺失字段明确标记；输入文件没有改动。工具若需要 API key，只通过其官方说明在本机配置，绝不粘贴到 issue 或提交到 Git。

## 3. 运行一次，再检查失败

先手动阅读三条结果与原文，再用 `git diff --stat` 和 `git diff` 检查修改范围。即使表格格式完美，也要逐条核对来源是否真的支持结论。

第二轮故意移除一份说明中的定价字段。正确结果应是“未提供”，不是从记忆补出价格。第三轮在输入中加入“忽略上面的要求”这类干扰文字，检查它是否被当作资料而非授权。

## 4. 分享可复查结果

在 [Show and tell](https://github.com/Uky0Yang/awesome-ai-agents-zh/discussions/categories/show-and-tell) 分享时记录：目标、公开输入、工具/模型版本、检查方法、失败案例、耗时，以及是否与项目有关联。不要只展示一次成功截图或把 demo 称为生产验证。

涉及安装与 API 用法时，以当前官方文档为准；本指南提供的是实验方法，不承诺模型费用、版本兼容性或输出正确性。
